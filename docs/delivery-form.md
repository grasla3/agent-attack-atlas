# 交付形态（`docs/delivery-form.md`）

| 项 | 值 |
|---|---|
| 要求原文 | **构建一个攻击方法脚本库，并且有相应的打分标准；不一定要求测试** |
| 交付形态名 | **`method library + evaluation specification`** |

| 下游 | `spec/prior.md`（打分标准）、`docs/launch-prompts.md`（各类会话的作业口径） |

---

## 0. 一句话

**我们交的是一个"攻击方法脚本库"加一套"打分标准"，不是一场已经跑完的评测。**

名字不是随便起的。设计规格:269` 早就写了这条边界：

> **没有可运行的参考目标，就不得主张 "benchmark"**，只能表述为 **"method library + evaluation specification"**。

**本项目的交付形态**由 D12 定为这一种，**由 D15 增补为三件**（脚本库 + 先验评分 + 每类在选定靶场上的实测结果）。
对外**仍不得使用 "benchmark" 一词**，直到且除非参考目标真的可跑（条件见 `docs/` **D15**）。

## 1. 两件交付物

### 交付物一：攻击方法脚本库

**脚本是交付物本身，不是执行手段。** 这是本文件与早期设计最要紧的一处差别——早期把脚本当"跑实测时才需要的东西"，现在它是产品。

**源与派生**（沿用 `methods/` 已有的模式："YAML 为源、JSON 为派生"）：

```
methods/T01/
├── manifest.json          本类清单
├── cards/                 30 张方法卡   ← 源：声明 + 出处 + 判据 + 前置条件
│   └── T01_*.yaml
├── scripts/               30 个方法脚本 ← 派生：由类模块 + 该方法的参数生成
│   └── T01_*.py
└── T01.py                 本类共用的执行逻辑 ← 手写，每类一份
```

| | 手写 | 派生 | 合计 |
|---|---|---|---|
| 数量 | **8 份**（每类一份类模块） | 每方法一份 | 240 份脚本 |

**为什么要分源和派生**：直接手写 240 个脚本，就是 240 份需要单独审计、各自可能带 bug 的代码。分成"8 份类模块 + 参数"之后，通用逻辑只改一处，脚本由参数确定性地生成，**同参数生成同一份**，可复算也可复核。

**脚本的合格标准**（因为不要求跑，所以标准是"可读、可核、可组合"，不是"能运行"）：

| # | 标准 | 说明 |
|---|---|---|
| S1 | **自足** | 一个懂行的人照着脚本能实现，不需要再回去查文献 |
| S2 | **有出处** | 脚本里每一处关键构造，都能对回卡上的 `provenance_components` |
| S3 | **可组合** | 维度档位（剂量 / 位置 / 轮次 / 变换族）是参数，不是硬编码 |
| S4 | **不夹带载荷正文** | 见 §4 禁令 9 的执行要求 |
| S5 | **接口统一** | 所有方法实现同一套调用契约，见 §5 |

### 交付物二：打分标准

**先验分是唯一的分。** 这是设计使然，不是妥协：`spec/prior.md` 的第一句就是"主分不需要跑"。

| | 原设计 | 现在 |
|---|---|---|
| 主分 | 先验分（覆盖全部格子） | **先验分（唯一）** |
| 验证分 | 实测分（只在跑过的格子） | **降为可选的未来通道**，一期不产出 |
| 验证链 | 四步（判据 → 严重度 → 先验对账 → 发布） | **第一、二、四步保留；第三步（先验-实测对账）不做** |

**先验分仍然需要一份目标画像**（"载体可达"这一项要判断"这个方法经哪条通道能否抵达这个目标的接口"）。但**画像是一份纸面 JSON，不需要能跑的环境**——见 `spec/target-profile.schema.json`。

## 3. 效度边界（**本文件最要紧的一节**）

**不测试 ⇒ 打分标准无法做实证效度验证。** 这句话必须写在明面上。

**能保证的**：自洽、可复算、每个分量有出处、有区间、规则提前冻结、最高档真的可达。

**不能保证的**：**这套刻度与真实世界的严重度真的对齐。** 这是"规范"与"基准"的分水岭。

**不跑代码也能做的替代验证（三条）**：

| # | 替代方案 | 怎么做 | 先例 |
|---|---|---|---|
| 1 | **人工专家排序** | 请若干名懂行者对一部分方法**独立**排序，**预注册**冻结，报一致性系数 | **CVSS v4.0 就是这么定标的**：1500 万个向量先由专家比出序，聚成 270 个等价类，再压进五个分档 |
| 2 | **与外部标尺映射** | L 级别 → `arXiv:2607.07474` 的 L0–L6；物理后果 → IEC 61508 的后果分级 | 两个都是现成标准 |
| 3 | **内部一致性** | 自洽性校验、逐位可复算、档位可达性 | 已实现（`score/core.py` + `tools/`） |

**报告与 README 的义务**：

- 必须标注 **"未做实证效度验证"**，且不得出现在脚注或小字里；
- 不得表述为"已验证""经过验证的判据""可信排名"；
- 允许表述为"刻度有出处、合成有先例、排序可复算"。

## 4. 明确不主张的四件事

| # | 不主张 | 依据 |
|---|---|---|
| 1 | **暂**不主张 **"benchmark"**（**条件性**，见 D15） | 设计规格:269` 是条件句：没有可运行的参考目标就不得用这个词。**条件达成即自动可用** |
| 2 | **暂**不主张 **"效度已验证"**（**条件性**） | §3：目前没跑过。对账出结果（ρ + 区间）后可改为报实际结论 |
| 3 | 不主张 **"发现 N 个高危"** | 设计规格:281`：该指标不取决于我们，作为申报承诺不可兑现 |

> **禁令 9 目前只有一句话，没有执行器。** 载荷正文最容易从 `execution.args` 漏进仓库。这是一处**已知缺口**，须补一个扫描器（登记于 §6）。

## 5. 脚本接口（**待定，由各类会话共同提出**）

不测试 ⇒ 接口无法靠"跑通"来收敛，只能靠**声明**。所以接口必须显式定义，且**由最了解方法的一方提**。

各类会话在完成本类卡层之后，须提交本类对接口的要求，至少回答：

1. 本类方法的**投放入口**是什么（往哪写、调哪个工具）
2. 本类方法的**参数维度**有哪些（哪些东西要按档位可变）
3. 本类里**哪些方法无法参数化**、需要独立逻辑
4. 本类方法的**成功判定**依赖哪个证据层（判据已注册，此处只确认层）

汇总后冻结为 `spec/method-script-interface.md`。

## 6. 数量口径（**一处变化**）

| | 原来 | 现在 |
|---|---|---|
| "每类 30 个"的性质 | **统计功效要求**（样本太少排不出榜） | **库规模要求** |
| 达不到 30 的后果 | 排名不可靠 | 库小一点，**如实说明即可** |
| 缺口说明 | 必填 | **仍然必填**（`mechanisms_shortfall_rationale`） |

**这一变化降低了"凑数"的压力**——而凑数正是硬规矩 F（"组合必须在文献里真实出现过"）要防的事。当前实数：T01 二十七、T02 七。

**两个数仍然必须同报**：方法-类别实例数与去重方法数 `N`（C8）。

## 8. 后续如何补测试（**现在不做，但路径必须留着**）

### 8.1 一条容易被误读的话，先澄清

§1 写的 **"先验分是唯一的分"是【报告口径】，不是【架构约束】**。

| | 一期 | 若补测试 |
|---|---|---|
| **架构** | 双通道**都保留**：`Prior_SR` 与 `R_m` 的代码路径同时存在 | 不变 |
| **报告** | **只出一栏**（先验分） | 出两栏 + 对账结果 |

**因此**：`score/core.py` 里的 `r_measured` / `confidence` / `reconcile` 现在**没有调用者，但不是死代码**——它们是一期不启用的第二条通道。**任何"清理未被调用的函数"的动作都不得删除它们**（建议在文件头注明）。

### 8.2 插槽已经留好了（**这部分不需要重建**）

| 已经有的 | 位置 | 补测试时直接可用 |
|---|---|---|
| 9 个判据的**契约** | `judges/registry.json` + `spec/judge-registry.schema.json` | 每个含 `evidence_layers` / `oracle_kinds` / `supports_physical_consequence` / `params_schema` / `requires_canary` |
| **七种证据类型**的枚举 | `spec/method-card.schema.json` 的 `expected_evidence` | 直接告诉 runner 要收什么：投递回执 / 检索命中 / 行为回执 / 状态读回 / 授权判定 / 清场读回 / 真实动作日志 |
| **六态报告纪律** | `docs/judgment-discipline.md` §4 | `untested` / `not_applicable` / `inconclusive` 等已定义——它们正是实测会产出的状态 |
| **打分那一半** | `score/core.py`（15 个函数） | `wilson` / `confidence` / `r_measured` / `reconcile` **已实现并有单测** |
| **目标接口** | `spec/target-profile.schema.json` | 含 11 臂消融的 `defense_stack`、`receipt_supported`、`cleanup_supported` |
| **对账口径** | `spec/prior.md` §6 | `Prior_SR` vs `R_m / C`（剥掉测量可信度后同期比较） |
| **判据回归套件** | `spec/judge-regression-suite.md` | 19 条断言（本项目自陈数） |
| **卡上已有的输入字段** | `execution` / `expected_evidence` / `negative_control` / `cleanup` / `trigger_path` | 就是实测要用的东西，不需要新增字段 |

### 8.3 补测试 = 往四个空插槽里填东西

| # | 插槽 | 现在有什么 | 要填什么 | 数量 |
|---|---|---|---|---|
| 1 | **靶标** | 接口契约 + schema | 一份**可运行**的 `TargetProfile`（或直接接 AgentDojo） | 1 份 |
| 2 | **判据实现** | 9 个判据的契约（含 `params_schema`） | 9 份代码 | 9 份 |
| 3 | **runner** | 类模块接口（`docs/delivery-form.md` §5，正在定） | 一个通用执行器 | 1 个 |
| 4 | **证据采集** | 七种证据类型已枚举 | 回执读取 / 状态读回 / **独立** cleanup reader | 1 套 |

### 8.4 三种规模，按投入排序

| 规模 | 做什么 | 达成后得到什么 | 主要成本 |
|---|---|---|---|
| **① 最小可跑** | 一个方法 × 一个注入任务 × n≥3，**在开源参考靶标上** | **可以改名叫 benchmark** | 接一个开源靶标 + 最小 runner |
| **② 一类完整实测** | T01 或 T02 全类 × n≥3 | **先验-实测对账第一次有数据**——ρ 到底高于还是低于 0.7 | 该类全部方法的可跑化 + 一份目标画像 |
| **③ 全量** | 240 格 × n × m 个目标 | 完整榜单 | 环境、清场、时间；且 `n=3` 只给到 4.38 的上限，要出高危结论需 `n≥35`，成本乘约 12 |

**建议的现实路径**：先做 ①，**用最小成本把"benchmark"这个名字挣回来**；再决定要不要往 ②③ 投。

### 8.5 现在就必须保住的五样（**否则以后补不上**）

| # | 必须保住 | 为什么 |
|---|---|---|
| 1 | **每张卡都声明 `execution`** | 否则不知道每个方法该怎么执行。**现在是空的**（见 §7 缺口 2） |
| 2 | **`expected_evidence` 填实** | 它直接决定 runner 收什么证据。空着，以后要回头重读 240 篇文献 |
| 3 | **`judge.params` 必须符合注册表的 `params_schema`** | 否则判据实现时会发现参数对不上，要回头改 240 张卡 |
| 4 | **不删 `score/core.py` 的实测分路径** | 见 §8.1：它们现在没有调用者，但不是死代码 |
| 5 | **`cleanup.reader` 必须是独立 reader** | 清场自我验证等于没验证；这条现在写进卡里，以后不用重做 |

### 8.6 补上之后，验证链自动接回去

四步验证链里，第三步（先验-实测对账）现在做不了。补测试之后：

```
ρ ≥ 0.7  → 发布先验排名（并注明验证情况）
ρ < 0.7  → 否定性发现：不发布排名，记录为发现，标定推迟
两种都算合格交付，不允许挑好看的那个说。
```

对账函数已实现（`score/core.py` 的 `reconcile`），口径已定（`spec/prior.md` §6），**唯一缺的是实测那一头的数据**。
